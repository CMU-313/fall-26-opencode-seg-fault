## Requirement changes

| ID | Original requirement (P3) | Revised requirement | Why it changed |
|---|---|---|---|
| R4 | Setting OPENCODE_LEARNING_MODE to a recognized value (true, 1, false or 0, in any case) overrides both config files for that process only. It never writes to a config file, and the next run without the variable goes back to the config setting. | Setting OPENCODE_LEARNING_MODE to a recognized value (true, 1, false or 0, ignoring case and leading/trailing whitespace) overrides both config files for that process only. An empty value is treated the same as the variable being absent. It never writes to a config file, and the next run without the variable goes back to the config setting. | Checkability: the original did not say what a value with surrounding spaces or an empty value means, so a test over arbitrary values had no expected result for them. Still traces to O-10/O-11 (one-run override) and O-17 (typo handling). |
| R5 | Changing learning_mode while a session is open takes effect from the next message in that same session. Earlier messages and replies stay in the history unchanged, and switching back restores the previous behavior. | Changing learning_mode in a config file takes effect the next time opencode loads that project's config: the next time opencode is started in that project, or when it reloads its config. Until then, the running opencode keeps the setting it loaded. Messages and replies already in a session's history are never changed by the setting, and switching back restores the previous behavior from the next load. | Feasibility: opencode reads a project's config once when it loads that project and caches it for the rest of the run (`Config.state` in `packages/opencode/src/config/config.ts`). Sending a message or starting a new session does not re-read opencode.json; only a restart or a config reload does. Meeting the original "next message in the same session" would need file watching that the design does not have. Keeps what we can guarantee from S-16/S-18 (history unchanged, switching back restores behavior). |
| R7 | If OPENCODE_LEARNING_MODE is set to an unrecognized value, opencode warns the user, naming the variable, the value it received and the accepted values, and keeps running with the config-file setting. | If OPENCODE_LEARNING_MODE is set to a non-empty value that is not recognized under R4, opencode logs one warning when it loads its config (normally once, at startup), naming the variable, the value it received and the accepted values, and keeps running with the config-file setting. | Checkability and consistency with revised R4: "unrecognized" is now defined by R4, so an empty value does not warn. "Once" follows O-20 (no repeated popups). Feasibility: opencode reports config problems through its logger (like the existing OPENCODE_PERMISSION warning), which writes to the log file and prints to the terminal only with --print-logs, so the acceptance criteria now say where the warning appears. |

R1, R2, R3 and R6 are kept as written: each is feasible in the current design, they don't conflict (R2 and R3 describe one precedence order: env > project > global > off), and each has acceptance criteria that can be checked against the request or the TUI. R6 is not implemented in the current code (the TUI has no learning-mode label yet), but nothing in the design prevents it; it is TUI behavior, so it is not covered by the property tests.
